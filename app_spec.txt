# Vektor Application Specification

## 1) Mission and Operating Model

Vektor is a deterministic, ML-first paper-trading firm engine.

The core requirement is explicit:
- ML is not optional and not advisory.
- Every trading intent must be generated by the deterministic ML decision stack.
- AI agents remain available only for non-deterministic functions:
  - trade-intent knowledge-base storage
  - detailed research/report generation
  - financial research writing
  - blog and publication workflows

OpenClaw orchestration for direct trade decisioning is removed from production paths.

## 2) Core Product Goals

1. Produce robust, mathematically auditable trade intents.
2. Fuse technical, fundamental, and sentiment analysis into one deterministic signal output.
3. Select and run the best-performing algorithm family for each market regime and symbol class.
4. Persist all data and outputs with lineage and reproducibility.
5. Operate as paper-first with strict risk constraints and hard safety gates.

## 3) Deterministic Trade-Intent Pipeline

Every cycle must execute this sequence:

1. Data integrity checks
- Verify market, fundamentals, and sentiment source freshness.
- Reject stale or fallback-only data when policy forbids degraded operation.

2. Technical analysis engine
- Compute broad indicator set (trend, momentum, volatility, volume).
- Detect structural patterns including:
  - breakout and mean-reversion formations
  - support/resistance context
  - liquidity pools/blocks and trap-like behavior proxies
  - multi-timeframe alignment

3. Fundamental analysis engine
- Parse balance sheet, income statement, and cash flow features.
- Compute quality, leverage, growth, profitability, and valuation factors.
- Apply domain-aware weighting by sector/domain profile.
- Forecast near-term fundamental drift with supervised models.

4. Sentiment analysis engine
- Aggregate multi-source sentiment (news outlets + investor/public channels).
- Move beyond simple polarity to event framing and reaction likelihood.
- Score expected market reaction window by timeframe horizon.

5. ML algorithm selection and training layer
- Evaluate regime and data-shape metadata.
- Select candidate model family from:
  - tree-based ensemble
  - time-series model
  - neural/deep architecture
  - reinforcement policy component where configured
- Use deterministic model registry and scoring rules to choose the active model.
- Persist model metadata, feature importance, confidence, and diagnostics.

6. Unified signal fusion layer
- Combine technical, fundamental, sentiment, and model outputs using deterministic weighting contracts.
- Produce one sole signal output for intent generation:
  - buy/sell/hold
  - confidence
  - expected horizon
  - stop/target hints

7. Policy and risk gate
- Enforce sleeve budgets, exposure limits, and mandate constraints.
- Permit no intent emission when data or model quality is below threshold.

8. Intent emission and persistence
- Write trade-intent record with full lineage links.
- Emit stream event and API response payload.

## 4) Data and Storage Requirements

Canonical stores:
- SQL (or configured relational storage) is source of truth.
- Knowledge graph is projection for retrieval and lineage queries.

Data requirements:
- Market bars/ticks, fundamentals snapshots, sentiment artifacts, model artifacts.
- Full run-scoped lineage IDs (`run_id`, `decision_id`, `order_id`, `report_id`).
- Backfillable/replayable ETL with observability endpoints.

Database validation must support:
- row counts by table
- latest timestamps per domain
- feature coverage checks
- model artifact existence and readiness

## 5) API Requirements

Backend must expose deterministic operational endpoints including:
- health and readiness
- data pipeline status
- model status and diagnostics
- strategy signal output with full diagnostics
- paper broker positions/orders/equity
- knowledge/development logging and query endpoints

OpenClaw endpoints in fund routes must remain disabled or removed from trade decision paths.

## 6) Frontend/Admin Requirements

The UI must reflect backend truth and provide:
- model readiness and signal diagnostics views
- technical/fundamental/sentiment component breakdown
- current policy/risk gate status
- pipeline/data freshness state
- no deceptive "green" states when backend quality gates fail

## 7) Runtime and Process Requirements

Long-running Codex workflow is mandatory:
- Each turn starts with bearings bootstrap.
- Work one highest-priority pending feature at a time.
- Validate through real outputs (API/UI/tests) before marking pass.
- Record START/END entries in Dev_Logs.md.
- Keep progress in codex-progress.txt.

Required root files:
- app_spec.txt
- feature_list.json
- codex-progress.txt

Sub-repos (`backend`, `frontend`) must retain matching init workflow setup.

## 8) Quality and Validation Requirements

Minimum quality bar:
- deterministic, reproducible calculations
- explicit score outputs and model diagnostics
- no silent fallback behavior for critical decision paths
- test coverage for policy gates, signal fusion, and failure states
- clear, queryable audit trail for each emitted trading intent

Verification categories:
- functional behavior
- style/UX integrity for operator surfaces
- data integrity and database completeness checks
- model selection correctness and output quality checks

## 9) Non-Goals

- No live trading activation in this phase.
- No placeholder "AI signal" optionality for trade intent generation.
- No undocumented ad hoc model path that bypasses deterministic contracts.

## 10) Definition of Done for This Spec Baseline

This spec baseline is complete when:
1. feature_list.json exists with 200+ ordered tests (functional + style).
2. All tests begin with `passes: false`.
3. Bootstrap scripts require `codex-progress.txt`.
4. Workflow docs/prompts refer to Codex-only naming.
5. Progress tracking file exists and is actively updated each session.
