## 1. Executive Summary

Vektor is currently a deterministic, ML-first, paper-trading fund engine with a FastAPI backend, a Vite/React operator frontend, a local SQL-backed warehouse, a knowledge graph projection, a paper broker, a deterministic core engine, admin/operator panels, and repo-local long-running Codex workflow harnesses.

The current product direction is not "AI chat picks trades." The app specification says trading intent must come from the deterministic ML decision stack. AI/agent surfaces are still present, but their intended role is research, summaries, publication, knowledge storage, and operational support. The deterministic signal path is the authority for trade intent.

The most recent backend change made the market-data path stream-first:

- `QuantDataPipeline.start()` now starts the Alpaca market stream itself.
- When `ALPACA_STREAM_ENABLED=true`, the pipeline reports `mode=live_stream_first`.
- Scheduled REST cycles are disabled as the freshness driver in stream mode.
- REST polling is now an explicit `fallback_polling` path only when streaming is disabled.
- The core engine overlays the latest persisted stream price into point-in-time market snapshots before deterministic signal evaluation.

## 3. Runtime Startup Flow

Backend startup lives in `backend/app/main.py` in `startup_event()`.

On startup, the backend:

1. Configures the event loop for agent-event websocket broadcasting.
2. Starts an automated devlog session.
3. Initializes the database.
4. Restores the knowledge graph projection from storage.
5. Enforces strict real-data mode outside dev unless deterministic runtime mode allows otherwise.
6. Restores:
   - decision ledger
   - audit log
   - research memory
   - sentiment store
   - performance tracker
   - task bus
7. Backfills the knowledge graph from persisted fund state.
8. Restores paper broker state from the database.
9. Starts the market websocket loop.
10. Starts the quant data pipeline.
11. Starts legacy auto trading only if enabled.
12. Starts fund agent runtime only if enabled.
13. Starts performance tracker if enabled.
14. Ensures the alpha model is available.

16. Logs fund stats.

## 5. End-to-End App Flow

This is the current intended path from startup to paper order.

### Step 1: Runtime Starts

`backend/app/main.py` initializes the database, state stores, broker, performance tracker, websocket stream loop, data pipeline, optional agent runtime, and model status.

The runtime is designed to be restart-safe: decision ledger, audit log, research memory, sentiment store, performance snapshots, task bus, broker state, and knowledge graph projections are restored from persisted storage.

### Step 2: Realtime Market Data Enters

The stream path is centered around:

- `backend/app/data/market_data.py`
  - `AlpacaRealtimeFeed`
  - `start_stream()`
  - `_run_stream()`
  - stream callbacks
- `backend/app/websocket/stream.py`
  - websocket broadcast loop for frontend clients
- `backend/app/data_pipeline/service.py`
  - `QuantDataPipeline.start()`
  - `_subscribe_to_stream()`
  - `_start_market_stream()`
  - `record_market_stream_event()`
  - `record_realtime_tick()`
  - `record_realtime_quote()`
  - `record_realtime_news()`

The stream-first contract now works like this:

- The pipeline subscribes to `FEED`.
- The pipeline starts the market stream.
- Incoming trade ticks are stored as raw events, market prices, quality events, provider health, and execution feature vectors.
- Incoming quotes are stored as quote rows, NBBO snapshots, quality events, provider health, and quote feature vectors.
- Incoming stream news is stored as raw events and text/news events.
- The status endpoint exposes whether stream mode is active.

REST still exists, but it is not supposed to be the normal freshness driver when streaming is enabled. It remains necessary for:

- cold-start history
- bars
- fundamentals
- news backfill
- disabled-stream fallback
- provider outage fallback when explicitly allowed

### Step 3: Data Is Stored

The SQL warehouse is in:

- `backend/app/data_pipeline/warehouse.py`
- schema in `backend/app/storage/schema_sql.py`

The warehouse stores:

- raw provider events
- latest and historical market prices
- market quotes
- market bars
- text/news events
- fundamentals
- quality events
- engineered feature vectors
- data pipeline runs
- provider health
- replayable snapshots

The reportable warehouse path is local SQLite right now. The docs and status guidance say SQLite is acceptable for local development and small universes, but Postgres plus TimescaleDB should be used for institutional continuous ticks, larger history, or multi-asset scale.

### Step 4: Quality Checks Run

Quality checks live under:

- `backend/app/data_pipeline/quality.py`

They validate:

- price observations
- bars
- quotes
- text/news events
- fundamentals

Quality output feeds:

- warehouse quality events
- provider health
- feature-vector category selection
- policy and freshness diagnostics

### Step 5: Core Engine Builds a Point-In-Time Snapshot

The core-engine snapshot path lives in:

- `backend/app/core_engine/feature_store.py`

It builds an `EngineInputSnapshot` using:

- market history
- latest persisted stream price overlay
- fundamentals
- latest news
- model versions
- data freshness metadata
- quality flags
- lineage IDs

Recent change:

- latest stream price from `data_market_prices` with `source_mode=stream` is overlaid onto the market history before signal evaluation.
- This prevents deterministic decisions from ignoring the freshest stream-backed price.

Remaining caveat:

- Bars, fundamentals, and latest news still use backfill/polling style sources.
- That is acceptable as support data, but the next hardening step should move more decision inputs toward warehouse-first retrieval and freshness gates.

### Step 6: Deterministic Core Engine Runs

Core engine entrypoint:

- `backend/app/core_engine/__init__.py`
- function: `run_core_engine(symbol, profile=None)`

The core engine runs:

1. `build_point_in_time_snapshot()`
2. `run_technical_pack()`
3. `run_fundamental_pack()`
4. `run_sentiment_pack()`
5. `run_meta_intent()`
6. `apply_deterministic_policy()`
7. returns `CoreEngineResult`

The output includes:

- symbol
- timestamp
- score
- action
- confidence
- subscores:
  - technical
  - fundamental
  - sentiment
  - ML/meta-intent
- model metadata
- diagnostics
- policy result
- freshness
- lineage
- deterministic contract hash
- reason codes

Important current guarantees:

- `signal_pipeline_only=true`
- `llm_signal_path=false`
- `mandatory_ml=true`
- technical path uses learned market-pack inference, not legacy indicator scoring
- fundamental path uses `learned_fundamental_pack_linear`, not legacy rule scoring
- policy rejections are explicit

### Step 7: Policy Gate Applies Risk Rules

Policy gate modules:

- `backend/app/core_engine/policy/deterministic_policy.py`
- `backend/app/fund/policy_gate.py`

The policy layer blocks or restricts intent based on:

- confidence
- expected utility
- stale data
- missing fundamentals timestamps
- missing or stale sentiment
- live trading prohibition
- notional size
- cash availability
- portfolio state
- asset-class and strategy-family thresholds
- risk breaker state

The system is paper-first. Live trading is not active in this phase.

### Step 8: Manual or Agent-Initiated Paper Order Uses Orchestrator

Fund orchestrator:

- `backend/app/fund/orchestrator.py`
- method: `FirmOrchestrator.execute_manual_paper_order()`

This method:

1. Normalizes symbol and side.
2. Resolves price.
3. Creates deterministic thesis, decision, risk, and intent IDs.
4. Resolves/reuses a deterministic ML signal artifact.
5. Extracts decision scoring and model versions.
6. Creates a decision ledger record.
7. Builds an `AdapterExecutionIntent`.
8. Runs policy gate checks.
9. Records pre-trade audit details.
10. Blocks with explicit reasons if policy fails.
11. Executes through the shared adapter path if approved.
12. Records paper order execution events.
13. Returns a full response with IDs, policy metadata, scoring, and deterministic signal payload.

Recent hardening:

- manual `/paper/order` execution now delegates to `FirmOrchestrator.execute_manual_paper_order()`
- orchestrator reuses provided signal artifacts instead of recomputing when symbol matches
- signal drift between approval and execution is reduced
- manual execution uses core-engine policy IDs instead of legacy risk-engine naming

### Step 9: State and Lineage Are Persisted

Important persisted systems:

- decision ledger
- audit log
- knowledge graph
- research memory
- sentiment ingest/store
- task bus
- performance tracker
- broker state
- data warehouse

This is why the app can restore paper positions and historical decisions after backend restarts.

### Step 10: Frontend Displays Operator Truth

The frontend is a Vite/React app. Key pages and surfaces:

Admin control center currently includes:

The design has been repeatedly tightened to be a professional black/white/gray operator surface with less decorative noise and better desktop/mobile behavior.

## 11. Current Known Risks

### Runtime/Code Drift

Before the service restart, the backend process was still running the old scheduled pipeline behavior even though the repo had the stream-first commit. Restart fixed the live local process. Future handoffs should verify live endpoint response shape after backend changes, not just tests.

### Stream Counters

After restart, `mode=live_stream_first` and `stream.started=true`, but pipeline-local `tick_count` and `quote_count` were still zero at the instant checked. Worker status did show a current provider event from `alpaca_stream`. Continue monitoring during active market/stream windows.

### Provider Health Timestamps

`data_provider_health` rows still include older 2026-05-15 successful stream timestamps. Current provider status can be fresher in `data_integrity.last_event` than in warehouse provider-health rows. This should be normalized so one operator panel does not show stale health while another shows fresh stream events.

### Agent Runtime Disabled

The fund OS has roles and task orchestration, but current local runtime has agent workers disabled. Any claim of active multi-agent autonomous operation would be false in the current live state.

### AI Role Adapter Disabled

AI role adapter is configured but disabled. This is compatible with the deterministic trade-intent contract, but research/blog workflows need explicit enablement and provider configuration.

### Backfill Inputs

Market price freshness is stream-first now, but bars, fundamentals, and news backfill still exist. The system should keep labeling those inputs and block decision paths when freshness fails policy.
